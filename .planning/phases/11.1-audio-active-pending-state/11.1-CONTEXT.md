# Phase 11.1: Audio-Active Pending State - Context

**Gathered:** 2026-04-19
**Status:** Ready for planning

<domain>
## Phase Boundary

Дана фаза впроваджує "передчасну" реакцію UI на голос (VAD-triggered segments). Основна мета — показати порожній сегмент (бабл) у списку транскрипції ТУТ І ЗАРАЗ, як тільки виявлено голос, не чекаючи перших токенів від ASR або підтвердження діарізатора.

Це забезпечує відчуття "миттєвого відгуку" системи (latency < 400ms), навіть якщо нейронна мережа Whisper/Parakeet потребує 1-2с для запуску декодування.

</domain>

<decisions>
## Implementation Decisions

### [ARCH] Dual-Source VAD Architecture
- **D-01: Microphone VAD (High-Frequency Level Stream):** `DualChannelAudioCapture` надає новий callback `onMicrophoneLevel` (викликається кожні ~93мс з `processMicrophoneBuffer`). `MeetingRecorder` використовує цей потік рівнів у приватному `MicVADMonitor` для детекції голосу (поріг -45dB, debounce 200ms). Це забезпечує реакцію UI значно раніше, ніж закриється 5-секундний ASR-чанк.
- **D-02: System Audio VAD (Diarizer Gate):** Роль VAD для системи виконує `SpeakerBufferManager`. Він викликає `onSpeechDetected` callback у `MeetingRecorder`, як тільки діарізатор підтверджує наявність голосу (150ms вікно). Це запобігає реакції на системні звуки (сповіщення).
- **D-03: Lifecycle Management:** `MeetingRecorder` зберігає `pendingMicSegmentId` та `pendingSystemSegmentId`, щоб не створювати дублікати під час активної фази мовлення.

### [ARCH] Reconciliation & Cleanup
- **D-04: Reconciliation (ID-First):** `processAudioChunk` та `transcribeClosedBuffer` використовують `pendingMicSegmentId` / `pendingSystemSegmentId` як ПРІОРИТЕТНИЙ механізм зв'язку з VAD-сегментом. Якщо ID відсутній, використовується fallback-пошук по `startTime` з розширеним вікном **~6 секунд** (тривалість чанку + запас), щоб уникнути дублікатів при зміщенні початку мовлення всередині чанку.
- **D-05: Ghost Cleanup Timer:** `MeetingRecorder` запускає 2-секундний таймаут для кожного VAD-сегмента. Якщо через 2с після припинення активності сегмент все ще порожній (`text == ""`) — він видаляється через `MeetingSession.removeSegment(id:)`. Це прибирає "сиріти" від коротких шумів або галюцинацій ASR.

### [UI/UX] Visual States & Shared Row
- **D-06: Shared Component Animation:** Оновити `TranscriptSegmentRow` (спільний для Notes та Detail view).
- **D-07: Pending Visuals:** Якщо `segment.isPending == true`:
    - Показувати пунктирний бордер (`StrokeStyle(dash: [4, 4])`).
    - Якщо `text.isEmpty`, показувати анімовані "typing dots" (...).
- **D-08: Simultaneous Support:** UI підтримує паралельні порожні сегменти для Mic та System (overlapping speech).

### [BEHAVIOR] Precision & Fallbacks
- **D-09: Fallback Creation:** Якщо VAD пропустив початок мовлення, ASR-шлях (`processAudioChunk`) створює сегмент самостійно (стара логіка як fallback).
- **D-10: Teardown Awareness:** Механіка очищення "ghost" сегментів не повинна заважати фінальному флушу (`stopRecording`), де дані мають бути збережені навіть якщо вони коротші за таймаут.

### Claude's Discretion
- Конкретна реалізація `MicVADMonitor` (простий RMS-лічильник vs vDSP).
- SwiftUI анімація для пульсації бордера.
- Внутрішні назви методів для сигналізації VAD у `MeetingRecorder`.

</decisions>
