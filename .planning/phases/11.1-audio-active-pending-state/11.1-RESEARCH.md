# Phase 11.1: Audio-Active Pending State - Research

**Researched:** 2026-04-19
**Domain:** Real-time Voice Activity Detection (VAD), UI Responsiveness, SwiftUI Animations
**Confidence:** HIGH

## Summary

This phase implements a multi-stage "pending" state for transcription segments to achieve near-instantaneous visual feedback (< 400ms) upon speech detection. Currently, the UI waits for the first ASR tokens (which can take 1-2s) before showing a bubble. By using a simple RMS-based energy gate, we can "pre-create" an empty segment that immediately signals to the user that the system is listening.

**Primary recommendation:** Use `vDSP` from the Accelerate framework for low-latency RMS calculation in the audio capture thread, and implement a reconciliation layer in `MeetingRecorder` to link VAD-triggered segments with subsequent ASR results using pending segment IDs (ID-first, with timestamp fallback).

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Energy Thresholding (RMS) | Audio Capture (Non-blocking) | — | Must run on the high-priority audio callback thread to avoid lag. |
| VAD State Machine | VADStateMachine (new actor) | — | Pure logic actor; isolated from coordinator concerns. |
| VAD Coordination & Segment Creation | MeetingRecorder | — | MeetingRecorder owns `pendingMicSegmentId`/`pendingSystemSegmentId` state and coordinates VAD → Session. Placed here (not MeetingSession) because coordination requires access to both the pending ID state and the transcriptCallback — both of which are MeetingRecorder concerns. MeetingSession does not have visibility into the recording lifecycle. |
| Ghost Removal Timer | MeetingRecorder | — | Ghost cleanup tasks are owned by MeetingRecorder (not MeetingSession) because they must be cancelled when ASR takes ownership of a segment — an event that occurs inside MeetingRecorder's processAudioChunk/transcribeClosedBuffer. Centralising cleanup in MeetingRecorder avoids a cross-actor cancellation protocol. |
| Segment Reconciliation | MeetingRecorder | MeetingSession | MeetingRecorder performs ID-first lookup; MeetingSession.removeSegment(id:) provides the deletion primitive. |
| Typing Animations | SwiftUI View | — | Visual feedback is a pure UI responsibility. |

## Architecture Patterns

### VAD Flow Diagram
1. `Audio Tap` (4096 frames) -> `vDSP_rmsqv` -> `dB value`.
2. `VAD State Machine` (in `VADStateMachine` actor):
   - If `dB > -45` for `> 200ms` -> Emit `speechStarted(time)`.
   - If `dB < -45` for `> 500ms` -> Emit `speechEnded(time)`.
3. `MeetingRecorder`:
   - `speechStarted` -> Create `MeetingSegment(isPending: true, text: "")` via `transcriptCallback`.
4. `ASR Chunk Processing` (in `MeetingRecorder`):
   - Check `pendingMicSegmentId` / `pendingSystemSegmentId` first.
   - Fallback: search for segment with `abs(segment.startTime - chunk.startTime) < 6.0s`.
   - Update text in-place via `MeetingSession.finalizeSegment`.

### Pattern 1: High-Performance RMS Calculation
**What:** Use `vDSP_rmsqv` to calculate Root Mean Square on the audio buffer.
**When to use:** Every audio callback (~10ms - 50ms intervals).
**Example:**
```swift
// Source: Accelerate Framework
var rms: Float = 0
vDSP_rmsqv(samples, 1, &rms, vDSP_Length(samples.count))
let db = 20 * log10(max(rms, 1e-7))
```

### Anti-Patterns to Avoid
- **Blocking the Audio Thread:** Never perform UI updates or complex logic directly in the audio tap callback. Use `Task` or `DispatchQueue`.
- **Frequent UI Over-updates:** Don't send level updates to the UI more than 10-20 times per second.

## Common Pitfalls

### Pitfall 1: Clock Drift
**What goes wrong:** VAD uses `Date()`, ASR uses `AVAudioTime`, and they drift.
**How to avoid:** Use a single source of truth for "recording start" (e.g., `Date()`) and calculate offsets from it consistently across both VAD and ASR paths. [CITED: developer.apple.com/documentation/avfoundation]

### Pitfall 2: Threshold Sensitivity
**What goes wrong:** Fixed -45dB triggers on fan noise or background clicking.
**How to avoid:** Implement a 200ms "stable signal" requirement (D-04). If the signal drops below threshold for even one frame during these 200ms, reset the timer.

### Pitfall 3: Fragmented Bubbles
**What goes wrong:** VAD triggers twice for one sentence, creating two bubbles.
**How to avoid:** Use a "hang time" (e.g., 500ms) after speech drops before declaring `speechEnded`.

## Code Examples

### VAD Debounce State Machine (Conceptual)
```swift
actor VADStateMachine {
    private let thresholdDB: Float = -45
    private let onsetDuration: Duration = .milliseconds(200)
    private let offsetDuration: Duration = .milliseconds(500)
    
    private var isActive = false
    private var lastTransition = ContinuousClock.now
    
    func update(levelDB: Float) -> VADAction? {
        let now = ContinuousClock.now
        if levelDB > thresholdDB {
            if !isActive && now - lastTransition >= onsetDuration {
                isActive = true
                lastTransition = now
                return .startSpeech
            }
            if isActive { lastTransition = now } // Reset silence timer
        } else {
            if isActive && now - lastTransition >= offsetDuration {
                isActive = false
                lastTransition = now
                return .endSpeech
            }
        }
        return nil
    }
}
```

## Open Questions (RESOLVED)

1. **Adaptive Threshold:** Should we use the `-50dB` noise floor from `MeetingWaveformView` as a baseline for the RMS gate?

   **RESOLVED:** Use fixed -45dB threshold. Adaptive threshold using -50dB noise floor from `MeetingWaveformView` is deferred. The -50dB floor is a waveform display parameter and not the right baseline for VAD — it tracks peak display amplitude, not a calibrated noise floor. False-positive risk on low-noise environments is better managed with the stable-onset requirement (200ms continuous signal above threshold), which already absorbs transient noise spikes. A fixed threshold is also easier to reason about in tests.
