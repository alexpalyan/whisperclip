```swift
import Foundation
import SwiftData

@Model
final class Prompt {
    @Attribute(.unique) var id: String
    var label: String
    var content: String
    var createdAt: Date

    init(id: String = UUID().uuidString, label: String, content: String, createdAt: Date = Date()) {
        self.id = id
        self.label = label
        self.content = content
        self.createdAt = createdAt
    }
}
```

Key decisions (from CONTEXT.md, locked):
- `@Attribute(.unique)` on `id` — enforces uniqueness in SwiftData store
- Default values for `id` (UUID) and `createdAt` (Date()) — existing call sites like `Prompt(label:content:)` continue to work
- No `Codable` conformance needed — SwiftData handles persistence
- No `Identifiable` conformance needed — SwiftData `@Model` provides it automatically via `PersistentModel`
- `import SwiftData` (not SwiftUI) — this is a pure model file

Create new file `Sources/SettingsDataContainer.swift` with the following content:

```swift
import Foundation
import SwiftData

@MainActor
enum SettingsDataContainer {
    static func create(inMemory: Bool = false) -> ModelContainer {
        let schema = Schema([Prompt.self])
        let configuration = ModelConfiguration(isStoredInMemoryOnly: inMemory)
        do {
            return try ModelContainer(for: schema, configurations: [configuration])
        } catch {
            fatalError("Could not create ModelContainer: \(error)")
        }
    }
}
```

Key design:
- `@MainActor` — SwiftData operations must happen on main thread (per RESEARCH.md pitfall #1)
- `enum` not `struct`/`class` — prevents accidental instantiation, this is a pure factory
- `inMemory: Bool = false` parameter — production uses `false` (SQLite on disk), tests use `true` (isolated, no cleanup needed)
- Schema references `Prompt.self` from the model file created in Task 1
- `fatalError` on failure is intentional — a corrupt ModelContainer at startup is unrecoverable

After creating the file, run `swift build` to verify both new files compile alongside the existing `struct Prompt` in SettingsStore.swift. The two Prompt types will temporarily coexist — the old struct will be removed in Plan 02. If there is a naming collision at compile time, temporarily rename the new class to `PromptModel` and add a `// TODO: rename to Prompt after removing struct from SettingsStore` comment. However, Swift should allow them to coexist if they are in the same module since one is a struct and the other is a class — but if the compiler complains, the rename is the fallback.

NOTE: If there IS a naming collision (likely since both are named `Prompt` in the same module), rename the new @Model class to `PromptEntity` in Prompt+SwiftData.swift and update SettingsDataContainer.swift accordingly. Plan 02 will rename it back to `Prompt` after removing the struct.
